## 1. P1：本地准备顺序可以永久分裂同一任务的共识摘要

**证据强度：运行复现确认摘要分裂及 proposal 拒绝；网络长期无法最终化由代码路径推导，未运行四节点乱序端到端试验。**

- `src/prepared.rs:444` 从本节点的全局 frontier 分配 Issue identity，LeakRepair 同样如此（502）。
- `src/prepared_plan.rs:274` 的 plan digest 包含实际分配地址、Transfer 选币和其他冻结计划。
- `src/runtime_submission.rs` 对收到的任务先独立 prepare，再开始共识；没有协调不同节点的准备顺序。
- `src/runtime_tasks.rs` 的私有拉取只下载原始 LegalTask，再以本地状态重新 `prepare_expected_plan`；已有同 TaskId 的 PreparedTask 如果摘要不同，只会拒绝，不采用远端计划。
- `BftDriver::accept_proposal` 要求 proposal 与本地 exact subject 一致。Coordinator 注册后也不允许同 scope 换 subject。

最小场景：相同 genesis、相同 ValidatorSet、相同两笔 Issue(A/B)。一组节点先准备 A 再准备 B，另一组先 B 再 A。A 在两组分别取得地址 1 和 2，两组 frontier 最后都为 3，但 A/B 的摘要均不同。四个节点按 2:2 分裂时，任何一个摘要最多取得两票，达不到三票 quorum；只轮换 proposer 不会使已有计划重新收敛。不同账户也能触发，原因是共享 allocator，并不要求资产争用。

复现程序断言同任务两个 plan digest 不同，并用实际 signer 构造有效 proposal，确认另一节点返回 `SubjectMismatch`。

修复边界：需要给冻结执行计划及其依赖提供协议认可的共同来源/协调规则，并验证与本地状态一致；不能通过跳过 digest 校验、随意覆盖已投票计划或退回已消费 identity 解决。具体协调方案需要设计，不能直接假定必须全网交易总排序。

## 2. P1：协议阶段没有 deadline，慢 peer 可以卡住发现和占满连接名额

**证据强度：bootstrap 阻塞已运行复现；128 连接耗尽场景为代码路径推导。**

- `src/runtime.rs:385` 顺序等待 `client_peer_records`，没有 request timeout。
- `src/runtime.rs:486-489` 等待 Hello 及第一条业务请求，没有阶段 timeout。连接 permit 在这些等待之前取得，公共和 BFT 连接共享 128 总额度。
- `src/network/quic.rs:245` 对 transport 启用 2 秒 keepalive。5 秒 QUIC idle timeout 不能替代应用请求 deadline；连接活着但应用不回应时，请求仍可一直等。
- `maintain_peers` 要等 bootstrap 返回之后才维护 BFT peers；公开发现中的慢 peer 因而也能延迟 Validator 连接维护。

复现：恶意服务端完成 TLS/Hello，收到 GetPeers 后保持连接但不回应。`runtime.bootstrap([恶意节点, 健康候选], 2)` 超过 7 秒仍未返回，健康候选未被连接。这已经超过现有 5 秒 idle timeout。

进一步场景：128 个不同身份连接完成 Hello 后不提交首条请求，可以长期占用 listener 名额。普通 NodeId 不要求 Validator 资格，因此攻击门槛是公开连接，不是掌握 Validator consensus key。

最小修复方向：Hello/首请求/发现请求使用有限阶段 deadline，超时释放 permit 并继续下一候选；任务分块上传需要整体或进度 deadline。保留长期正常公共/BFT 连接，不能用统一短连接寿命破坏长期通信。Validator 连接是否预留容量可另行评估，不能只扩大 128。

## 3. P1：私有任务拉取来源不响应时，重试实际不会切换来源

**证据强度：静态确认控制流；未做 Byzantine 网络复现。**

`src/runtime_bft/task_sync.rs:218`：只要 `fetch.current_source.is_some()`，`request_next_prepared_task_source` 立即返回。这个判断在 `reset_attempted` 处理之前。选择来源时即设置 `current_source`；`send_direct` 成功仅证明进入本地发送队列，不能证明对方返回任务内容。

runtime 每到 proposal 时间调用 `retry_prepared_task_sync(true)`，但上述提前返回使这个重试对正在等待的来源无效。没有记录 chunk deadline/last progress。来源只在明确拒绝、坏 chunk 或发送失败时重置；连接保持正常而请求无回应，或来源在异步发送成功后消失，都没有这条 fetch 的到期切换路径。

后果：目标任务不能在该节点安装；最多 32 个 fetch 名额长期被占用，后续新 scope 会被容量检查拒绝。Byzantine Validator 可以提供 announcement 后不响应 pull；正常来源中途故障也可能留下等待。

最小修复方向：给 fetch 保存进度期限；期限到后 reset source，尝试其他已授权来源；明确处理连接失效。只在确有 pending fetch 时使用现有 worker deadline，不加全库扫描后台循环。

## 4. P2：共识事件队列无界，CLI 长期进程从不消费

**证据强度：静态确认所有生产调用者。**

`src/runtime_bft_consensus.rs:352` 的 `events` 是无界 VecDeque。成功 finality、拒绝、未注册 scope 和发送失败都会追加（包括 486、495、777、786、814）。`drain_bft_consensus_events` 是公开 API，但生产 `src/cli_node.rs:68-71` 只等待 `runtime.run()`，没有消费；搜索 src 内也没有其他生产消费者。

因此正常持续成交已经会让事件数量按完成任务数增长；Byzantine Validator 可持续产生未注册/拒绝事件，加速增长。inbound queue 和 pending scopes 有界，不等于派生出来的事件队列有界。该问题不需要证明每条事件具体多少字节，也不应凭空给出耗尽时间。

最小修复方向：先明确事件是有限诊断历史还是必须可靠交付的业务通道。诊断历史应设容量/去重或让 CLI 消费；必须可靠交付则需要真实消费者和背压。不能静默丢弃持久业务真值来修一个诊断队列。

## 5. P2：peer 缓存原地截断写，崩溃后可使完整节点无法启动

**证据强度：启动拒绝已运行复现；写入中途断电未做故障注入。**

`src/network/peer_store.rs:96` 用 truncate 原地覆盖 `.peers`，直到最后才 sync。`PeerStore::load` 对任何存在但无效的内容直接返回错误，`NodeRuntime::bind_backend` 传播此错误而终止启动。

触发：写 `.peers` 时进程崩溃或磁盘写失败，文件留下空/半帧；主状态快照和投票安全状态仍完整，但节点启动被一个可重新发现的 reachability 缓存挡住。复现用已存在的节点数据写入 partial peer cache，再确认 `load_and_bind` 返回错误。

最小修复方向：peer cache 原子发布；对已确认属于缓存格式损坏的错误丢弃缓存并使用 bootstrap，其他 I/O 错误仍按实际错误处理。这不是兼容旧格式，也不能推广到主快照、投票锁或身份私钥损坏后自动清空。

## 6. P2：小公开请求反复触发全状态加载与全量摘要，分页同步代价随规模放大

**证据强度：静态复杂度分析，未做大状态性能基准。**

- `src/runtime.rs:659-677` 每个 public Currency 请求都 `StateStore::load`，再遍历全部 Currency，创建完整 PublicCurrencyView。
- `src/network/session.rs:440-457` 连 checkpoint proof 查询及一页 Currency 查询也经过此 loader。
- `slot::load_latest` 每次读取并完整解码两个快照槽；encode/decode 路径还验证各类状态链接及已有证据。
- `src/network/recovery.rs:112` 每个最多 60 KiB 的恢复 chunk 都重建完整 shared payload 并验证它是否仍匹配检查点。
- 每一次投票状态持久化又重新 encode 整个 snapshot，并刷新两个完整槽。

对 N 个 Currency 的完整分页同步，页上限 256；至少有约 N/256 次全量 N 规模遍历，因此这部分累计工作接近 O(N²/256)，还没有计入快照中的任务、签名证据和其他数据。固定大小 proof 查询也具有全状态成本。公开调用者无需 LegalTask 授权即可触发前者。

这里不能报一个虚构 TPS 数字，也不能说它已经导致当前数据规模超时；这是明确的放大路径。改进方向应沿现有 StateStore authority：按持久 generation 复用已验证派生结果、对 proof 请求避免构造 view、页查询利用已有索引、恢复传输复用已验证 immutable payload 并廉价确认当前状态。缓存失效必须覆盖跨进程写入，不能形成另一份资产真值。具体优化先测量，再实施。

## 7. P1：镜像退化后主槽损坏，会回退已输出 vote 的安全状态

`src/persistence/slot.rs:138` 忽略镜像刷新失败；load 则选择任意有效槽中的最高 generation。如果镜像失败后旧镜像仍有效，新主槽后来丢失/损坏，loader 会接受旧 generation，无法从槽内容证明它落后于已经输出的签名。当前没有外部 durable high-water mark 来检测这种回退。

**证据强度：Windows 文件故障注入已运行复现，确认已输出 finality vote 的锁丢失；未复现冲突双签。**

复现过程：先持久化某 public checkpoint 的 BFT finality-ready；把下一次写入的 mirror 文件设为只读，使 mirror refresh 返回 I/O 错误；调用真实 ValidatorSigner，成功取得 finality vote，确认主槽 generation 前进。随后向新主槽写入损坏内容，loader 自动回到先前 generation，且 `validator_safety_ready` 仍为 true。恢复 mirror 的可写权限后，对同一个 checkpoint 再次签名会重新写入一个 generation；如果原 vote lock 存在，这次签名应走 AlreadyLocked 而不产生写入。这个断言确认了 vote lock 已回退。

这需要“镜像退化后主槽再丢失”的组合故障，不能冒充普通单次 crash 双签漏洞。现有 snapshot checksum 能辨认内容损坏，不能辨认有效旧快照是否已落后于输出过的签名。修复前先明确故障模型：若允许这种退化恢复，恢复后必须保守锁住 signing safety，并通过现有 recovery/fence 机制再进入，或引入能可靠判定已提交安全状态下界的存储机制。不能草率把镜像失败直接返回普通未提交错误，因为主槽可能已经完成 durable commit；也不能简单禁用所有备用槽恢复而破坏正常 crash recovery。

另外，DESIGN.md:951 仍写 Full snapshot version 4，而 codec 常量和未发布格式规则是 1。这是文档漂移，不计入上面六个运行缺陷。

## 验证和边界

可运行复现：`cargo run --example audit_liveness`。它验证准备顺序摘要冲突、有效 proposal 被拒、超过 idle timeout 的 bootstrap 阻塞，以及坏 peer cache 阻止启动；Windows 下还执行 mirror 只读 + primary 损坏的实际投票锁回退试验。网络等待有 7 秒外层限制；断言失败以非零状态退出。复现只使用随机命名的临时存储，不操作用户节点数据。

原有本地测试通过：16 个单元测试（另有 1 个忽略的子进程 helper，实际由父测试运行）、217 个集成测试。新增复现也通过。`cargo fmt --all -- --check`、`cargo check --all-targets`、`cargo clippy --all-targets -- -D warnings`、`cargo test --all-targets` 及 `git diff --check` 均通过。

未做：四节点乱序长期压力试验、128 连接占满试验、Byzantine 私有拉取端到端试验、真实掉电、故障恢复后冲突双签、大状态基准。现有 happy path 全通过不能替代这些场景，也不能推出全项目已安全。

建议处理顺序：投票安全状态回退与冻结计划的跨节点收敛规则优先；再修网络阶段 deadline 和 fetch 切换；随后限制诊断事件并修缓存恢复；性能放大路径做真实规模基准后优化。不要把这些问题打包成一个盲目重构，尤其不能通过削弱 exact subject、finality lock 或身份验证来提高活性。
