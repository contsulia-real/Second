# CLI 钱包节点实现方案

2026-10-09 · 未确认的实现草案，以下命令与钱包能力尚未交付。完整仓库核对见 [project-review-2026-10-09.md](project-review-2026-10-09.md)。

## 第一版形态

提供独立的 `second-wallet` 程序，复用 Second 库的 NodeRuntime、身份、连接、认证公开状态同步、LegalTask 编码、签名、提交及任务查询能力。钱包以普通节点身份接入，默认不启用 Validator。它管理用户的钱包资料和原始请求，不默认复制完整私有网络状态，不维护第二份权威余额。

第一版采用单进程交互式 CLI：打开钱包后运行节点，命令在同一进程内执行，退出时关闭本进程的节点。暂不新增常驻后台钱包服务、IPC 控制端口或图形界面。初始化、导入和备份可以离线执行；账户和支付地址只有对应 LegalTask 成功提交后才能显示为已注册。

## 命令与用户流程

下列为拟议交互方式，不是当前可执行入口：

```text
second-wallet init ./alice --network ./network.json
second-wallet open ./alice

wallet> account create
wallet> address
wallet> balance
wallet> send pay_... 10
wallet> status <task-id>
wallet> history
wallet> exit

second-wallet backup ./alice ./alice-backup
```

`send` 展示付款账户、收款地址和数量，明确确认后生成唯一 TaskId。原始业务意图和签名请求在发往网络前持久化。超时、断连或程序重启后查询或精确重提同一请求，不另建任务补发。受理、准备、最终认证与成功提交分别显示；只有 `succeeded` 表示本次付款完成。余额未知、过期或查询失败时不显示为零，也不使用本地交易记录推算一个权威余额。

`history` 第一版记录这个钱包创建和保存的请求及查询结果，不承诺完整的全网收款历史。`backup` 保存钱包资料、签发材料及未完成请求；不复制 Validator 签票状态，不将钱包备份当作节点签名安全恢复凭据。备份含秘密时必须受限访问，拒绝覆盖已有目标。

## 分工与复用

- CLI 层处理输入、确认和结果显示。
- 钱包存储层保存账户与地址资料、配置和原始请求，采用原子写入和目录排他；不保存另一份可独立改变的余额账本。
- 钱包运行层组合既有普通节点、明确的可信网络参数和业务请求客户端；复用连接预算、身份验证和请求期限。
- Second 核心继续负责授权任务执行、最终性、持久化和公开/私有数据边界。钱包不会把业务保证金、服务商组织或商业仲裁塞进核心。

## 授权边界

第一版保持现有 AuthorizerSet 模型。钱包要取得网络认可的 LegalTask 签名：可以使用本地持有的受信任 Authorizer 材料，或导入按既有格式签好的请求。新生成一个节点密钥不会自动获得业务写权限。Authorizer 材料是签发者权限，不是账户私钥；界面、帮助和备份说明不得把它称为账户所有权证明，也不能保证其他受信任签发者无权操作该账户。

普通用户仅凭新生成的账户私钥控制资产、任意新签发者无需准入等能力，不是现有代码已经提供的事实。若以后要求这些能力，需要另行明确资产控制规则；本钱包草案不删除信任校验，也不静默新增账户密钥绑定。

## 真实余额接入：实现前必须闭合的接口

PublicStateStore 没有 Account owner 或 PaymentAddress 绑定，不能从公开状态推导个人余额。现有提交和任务状态客户端也不是余额查询接口。已有 Full 节点本地可以通过 StateStore 加载资产真值并调用 SecondState::balance，但读取 Validator 整份私有快照不作为普通钱包的接入方案。

完整源码核对后撤回此前自行提出的“原开户任务的签发者取得账户读取权限”规则，以及由此推导的 Genesis 账户查询限制。RegisterAccount 只注册账户标识，没有建立账户密钥或读取授权关系；AuthorizerSet 校验的是 LegalTask 签发者，不能从这两项现有能力推出上述权限。

SecondState::balance 已从 Currency.owner 统计账户余额。钱包需要确定的是采用哪种状态后端，以及怎样取得与该账户相关的已验证状态；不是另行实现余额账本。完整状态后端可直接复用本地统计，但本地存储访问不等于协议授予任意远端节点私有读取权限。公开状态后端不包含 owner，现有网络消息也没有账户余额读取接口。远端读取或选择性同步的权限和证明机制目前未确定，这份草案不替它们作决定。

不能凭 NodeId、任意签名或仅仅出示账户地址读取私有数据，也不能因为 Authorizer 被信任签发任务就默认为其授予全部私有查询权限。

结果应从节点的既有持久资产状态派生，标识回答节点和状态新鲜度。证书固定或对端认证证明回答者身份，不等于个人余额拥有独立 finality proof；不能把单节点回答宣传成无需信任的资产证明。个人资产的证明或选择性同步方案目前未实现，不为了展示钱包引入全量私有复制或重复共识。

余额接入属于钱包的新工作范围，不是对既有余额模型的否定。确定状态后端及访问方式之前，不能静默改变现有私有数据访问权限，也不能伪造余额或公开 owner 数据来宣称钱包已完成。

## 实现顺序与验收

1. 闭合私有账户读取的权限与结果语义，确定最小网络接口；同步协议说明。
2. 实现钱包资料、原始请求持久化和账户/地址创建流程。
3. 组合普通节点运行能力，完成真实余额、收款地址、转账、状态和本地请求记录。
4. 用真实节点验证两钱包收付款；断连后恢复原请求、重复提交不重复扣款、错误签名和无权限查询被拒绝、钱包重启及备份恢复。

测试只增加现有协议回归尚未覆盖的钱包行为和新的私有读取边界。代码变化按仓库现有本地 fmt/check/clippy/test 与 diff 检查执行；不以新增 CI、服务商、交易市场或商业保证金制度作为钱包交付前置。

本方案没有确定私有读取权限，也没有实现该接口或新增用户自托管规则。它保留钱包能力与既有模块的对应关系，不是已经交付的钱包或已经批准的授权协议变更。
